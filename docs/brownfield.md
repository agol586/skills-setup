# Initialize skills in an established project

Use this path when the target already has application code, released behavior, or established project rules. Installation is configuration work; the first documentation pass should describe the system that exists today.

1. **Preserve a baseline.** Run `python3 scripts/setup.py inspect --project <root> --agent <key>`. Read existing README, docs, agent instructions, CI, tests, deployment configuration, and Git status. Work from a reviewable branch or isolated worktree when the checkout has active changes. Record the release or commit whose behavior you are describing. The dry run shows commands; the real installer resolves live pack names and stops on same-name custom skill conflicts before target writes. Finish when pre-existing edits are visible in a baseline diff and managed-path conflicts have been checked.
2. **Install and verify the selected tools.** Run the selected installer dry run, then installation. Review changed files before writing project documentation. If existing `.specify/` is present, use its integration path; inspect constitution and customized managed files. Keep existing skill directories and agent instructions intact. Finish when the selected tools work and the application source and existing documentation have no unexpected changes.
3. **Trace the running system with CodeGraph.** For each important user or external entrypoint, run `codegraph explore "<entrypoint or flow question>"` from the indexed project. Use focused `codegraph callers`, `callees`, and `impact` where the first answer leaves a boundary unclear. Cross-check graph paths against routes, tests, configuration, persistence schemas, and deployment docs. Build a small inventory of components, service boundaries, data stores, external integrations, and the main request/background-job paths. Finish when every documented edge has a code or configuration reference, or is explicitly marked as an operational assumption to verify.
4. **Write the current architecture and logic.** Fit the target's existing docs convention; if none exists, use `docs/architecture/overview.md`, `critical-flows.md`, and `constraints.md`. The overview should identify components and responsibilities, boundaries, deployment/runtime assumptions, and links to existing docs. For each critical flow, record the trigger, ordered calls, state changes, error/retry paths, and observable outputs. The constraints document should separate verified contracts (API/schema compatibility, permissions, invariants, idempotency, performance or operational limits) from open questions. Attach `path:line` code/config references and test names to each claim. Business meaning that code cannot establish needs an owner or existing product/operations source. Finish when a maintainer can trace each critical behavior to evidence and see which claims remain unverified.
5. **Generate and validate diagrams with Archify.** Make a high-level `architecture` diagram from the verified component inventory and one `workflow`, `sequence`, `dataflow`, or `lifecycle` diagram for each flow where a picture clarifies boundaries or state. Store the typed JSON source and delivered HTML next to the architecture docs. Run Archify `validate` and `deliver`; for repository-backed architecture diagrams, pin a Git revision and source ranges and pass `--repo-root`. Link diagrams from the overview. Finish when the diagrams match the prose and validation passes.
6. **Turn facts into agent rules.** Derive Spec Kit constitution principles and project agent instructions from the verified constraints, retaining existing wording where it is already accurate. Add the CodeGraph-first navigation rule only for this indexed repo. Link the architecture, flows, constraints, and diagram entrypoint from the project's README or agent docs. Run the project's existing checks and review the full Git diff. Finish when the new workflow protects the current contracts and points future work at a bounded change, with open questions still plainly marked.

CodeGraph supplies structural code evidence, not product intent or the live deployment topology. Use release notes, runtime configuration, tests, and maintainers' existing documentation to resolve those facts. A diagram is a derived view of checked claims; preserve its source and verification context so it can be updated with the system.
